# 性能、资源与时序计量

## 先定义口径

| 指标 | 计算与约束 |
|---|---|
| 总线理想带宽 | `(TDATA位宽/8) × 实际接口时钟Hz`，仅理想上限 |
| 窗口有效带宽 | 成功握手的 TKEEP 保留字节 ÷ 完整连续窗口时间，包含窗口内复位时间 |
| 活动期有效带宽 | 同上字节数 ÷ 非复位观测周期时间；不能与包含复位的指标混写 |
| 数据字节 | TKEEP 与 TSTRB 同时置位的字节；位置字节单独对待 |
| 握手利用率 | 成功握手周期 ÷ 非复位观测周期 |
| 反压占比 | valid=1/ready=0 周期 ÷ 非复位观测周期 |
| 供数气泡 | valid=0/ready=1 周期数，表示接收端可接收但当拍未供数 |
| 双低周期 | valid=0/ready=0，单点不能唯一归因 |
| 延迟 | 起点终点必须明确：首入到首出、首入到末出或主机提交到可用结果 |

只在连续、完整时钟采样且频率已知时计算时域带宽。稀疏 CSV、只保存有效拍的 ILA 不能按文件行数当时间；工具将其带宽、利用率及反压占比置为 null，计数只表示已观察样本，最长连续反压仅是下界。多时钟域不直接相减各自 cycle。

当前 trace 脚本给出握手、字节、状态占比、最长反压及带宽；不自动匹配输入输出事务算算法延迟。硬件延迟需用关联事务/帧序号及共同时基另行测量，再把明确口径的结果交给 benchmark 汇总。

## 计时范围

- `hardware`：由受控硬件时基或连续波形计算的区间；记录输入输出事件定义。
- `dma`：经过明确隔离的搬运时间；若流水线计算和 DMA 重叠，不能直接把总耗时称作纯 DMA 时间。
- `python_e2e`：软件时钟包含所调用的缓存同步、启动、轮询和结果同步。`board_session.run_simple` 的区间从缓存准备完成后开始，包含寄存器提交、启动和接收 invalidate；不包含分配、生成测试数据、黄金比较和文件写入。

不要用 Python 端到端耗时推算硬件流水线 II。板上模板记录每次测量；benchmark 按 scope 和 payload 字节数分组。bytes 约定为一次单向业务有效载荷，回环不能把发送与接收相加夸大吞吐。

## 基准流程

1. 固定设备、版本、构建哈希、频率、数据布局及测量口径，先验证数据正确。
2. 保留原始预热样本，汇总时用 `--warmup N` 丢弃文件开头 N 条；多个场景分别记录，避免混合文件中只丢一次预热。
3. 对包长、批量数、连续包数、必要的 FIFO/频率配置做单变量比较；频率改动应在授权范围内重新验证约束。
4. 输出样本数、最小/中位/P95/最大延迟、合计字节除以合计时间的带宽。P95 用排序后的线性插值，小样本不代表稳定的长尾结论。
5. 对优化前后使用同数据、同计时边界、同预热次数和重复次数；保持正确性回归。标注测量误差、轮询间隔和共享 DDR 负载。

## 瓶颈定位

反压多：沿下游查看接收 DMA、FIFO 满、DDR 响应、计算输出。供数气泡多：沿上游查看 DMA 供数、软件调度、计算 II 或输入源。单点占比只能缩小范围，不能唯一判定 DDR 或某个 IP。

真实源峰值速率与平均速率分开计算。有限 FIFO 可以吸收有限突发，不能修复长期平均输入速率大于服务速率的问题。`fclk/II` 是忽略边界、补边和停顿的处理速率上限；帧率还受尺寸与协议开销影响。

## 资源和时序

`collect_resources.py` 提取 Vivado 利用率报告中的 LUT、寄存器、BRAM、DSP 原始表行和 timing summary 小块，并附 SHA-256。它不生成综合/实现，也不把无法识别的格式补成数字。

报告必须记录综合还是布局布线、器件型号、时钟、构建哈希及工具版本。完整结论检查 setup、hold、pulse/min-period、未约束路径、时钟/输入约束、CDC 和例外。资源与 timing 报告应属于同一构建。

项目历史中已出现 WNS 为正但 HDMI pulse/min-period 仍失败的情况；这只能称为局部约束检查结果，不能称完整时序收敛。该经验不意味着其他板卡具有同样限制。
